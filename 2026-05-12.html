Everything Gets Rewritten

Npm packages compromised through a GitHub Actions exploit chain, AI discovers a curl bug while criminals use the same technology offensively, GitLab eliminates three management layers, and a quiet consensus is forming that software engineering may be more like professional sports than any of us wanted to admit.

📰 Hacker News 🎙️ YouTube

The Build Pipeline Is Now the Attack Surface

Yesterday, TanStack — the suite of high-quality React primitives used by hundreds of thousands of projects — published a thorough postmortem on a supply-chain attack that compromised 84 package versions across 42 @tanstack/* npm packages in a six-minute window. It's worth reading in full, because the attack chain is a textbook case of how modern CI/CD infrastructure turns trust into a liability.

The attacker's method was elegant in its nastiness. It relied on three distinct vulnerabilities stacked in sequence. First, a pull_request_target "Pwn Request" — GitHub Actions workflows that use this trigger run with the base repository's secrets even for PRs from untrusted forks, bypassing the "first-time contributor approval" gate that many maintainers assume is protective. Second, GitHub Actions cache poisoning: by force-pushing to a PR, the attacker triggered a workflow that cached a 1.1 GB poisoned pnpm store keyed to the main branch scope, not the fork's scope. Third, once that cache was in place, legitimate runs on main pulled it and executed the payload — which extracted an OIDC token from runner memory and used it to authenticate npm publishes.

The malware itself was comprehensive. Running on install, it harvested credentials from AWS IMDS, GCP metadata, Kubernetes service account tokens, Vault tokens, SSH private keys, and npm credentials. Exfiltration happened over the Session messenger's file-upload network (end-to-end encrypted, no C2 to block). It self-propagated by enumerating other packages the victim maintained and republishing them with the same injection.

"Because the payload runs as part of npm install's lifecycle, anyone who installed an affected version on 2026-05-11 must treat the install host as potentially compromised." — TanStack postmortem

There are two layers of irony worth noting. The malicious commit was authored by the identity claude <claude@users.noreply.github.com> — likely chosen to blend into a codebase where AI-authored commits are unremarkable. The other irony: the attack was detected within 20 minutes by an external researcher, not by GitHub or npm's own systems. The community caught it faster than the infrastructure did.

The immediate lesson is narrow: audit every pull_request_target workflow you own, scope your caches properly, and be suspicious of PRs with [skip ci] prefixes from new contributors. But the broader point is harder to ignore. The supply chain is the software now. CI/CD pipelines, package registries, and GitHub Actions runners are infrastructure of a similar criticality to production databases — and they're being managed with far less security discipline. Every time the industry adds another layer of automation, the attack surface for that automation grows proportionally.

AI Finds the Bugs — Both Sides Know It

Two stories landed this week that, read together, paint a picture of where AI security capabilities are heading. In April, Anthropic's Mythos model — their restricted-access AI specifically trained to find vulnerabilities in source code — began being used by select open-source projects through a partnership with the Linux Foundation's Alpha Omega initiative. Daniel Stenberg, the lead developer of curl, finally received a report: Mythos found exactly one vulnerability.

This is notable for what it says about both the capability and the maturity. Curl has already been scanned by AISLE, Zeropath, OpenAI Codex Security, GitHub Copilot, and Augment — these tools have collectively triggered somewhere between two and three hundred bugfixes over the past 8–10 months. Mythos, on a codebase that has been intensively hardened by prior AI tools, still found something the others missed. One vulnerability in a deeply audited project is not a failure of the model; it's a demonstration that even well-scanned code has residual risk, and that different models find different classes of problems.

The other story cuts in the opposite direction. The New York Times, citing Google, reported that criminal hackers have been using AI to find a major software vulnerability — not for defensive purposes, but for exploitation. The specifics of the vulnerability haven't been disclosed, but the pattern is clear: the same model capabilities that power defensive scanning are equally available to offensive actors.

This is the dual-use problem in concrete form. Anthropic kept Mythos restricted precisely because of this concern — giving a large population of attackers the same code-auditing capability that defenders had just acquired would collapse any temporary advantage. But restrictions on frontier models don't prevent earlier-generation models from being fine-tuned or prompted for offensive security research. The gap between defensive and offensive AI capability is narrowing, and the defensive side has a structural disadvantage: it needs to find every vulnerability, while attackers only need to find one.

"Before this first Mythos report, we had already scanned curl with several different very capable AI powered tools… These tools and the analyses they have done have triggered somewhere between two and three hundred bugfixes merged in curl." — Daniel Stenberg, curl maintainer

The practical upshot for software teams: AI-powered vulnerability scanning is no longer optional. The question isn't whether to run it; it's which tools, on which cadence, and how to prioritize the results. Projects like curl that have already integrated multiple scanners are ahead. Most projects haven't started.

GitLab's "Act 2": What Restructuring Actually Looks Like

GitLab published a letter to customers and investors announcing significant workforce restructuring. Buried beneath the standard corporate framing is a description of what an AI-era reorganization looks like in practice, and it's more specific than most.

Four changes. First: reducing operating countries by up to 30%, consolidating where GitLab has only small teams and replacing physical presence with partner networks. Second: removing up to three layers of management in some functions — described as getting leaders "closer to the work." Third: reorganizing R&D into roughly 60 smaller, empowered teams with end-to-end ownership, nearly doubling the count of independent teams. Fourth, and most telling: "rewiring internal processes with AI agents, automating the reviews, approvals, and handoffs to speed us up, and plan to right-size roles across the company to follow suit."

That last phrase — "right-size roles" — is doing significant work. It means that some of the roles currently dedicated to reviews, approvals, and coordination handoffs are being eliminated, because an AI agent will handle the coordination. The three layers of management removal and the doubling of independent teams are structurally consistent with this: if agents handle the coordination overhead that managers previously absorbed, you can run more teams with fewer management layers. The org structure that made sense when human coordination was the bottleneck is being restructured around AI coordination as the default.

GitLab did confirm Q1 and full-year guidance, so this isn't distress restructuring — it's intentional transformation. What's significant is that GitLab builds developer tooling and lives close to the bleeding edge of agentic software development. If they think the internal org structure that made sense in 2023 doesn't fit 2026, that's a signal about where the rest of the industry is heading.

How Claude Code Was Born: Building for the Model Six Months From Now

Boris Cherny — the engineer who built Claude Code (referred to internally as "QuadCode" during development) — gave a talk at Y Combinator earlier this year that's worth examining for what it reveals about how the most influential developer tools of this era get made. His account is a study in accidental invention and disciplined conviction.

The origin is almost comically modest. Cherny wanted to understand the Anthropic API — he hadn't used it before. So he built a small terminal app to interact with it. It was a chat app. That's all. When tool use shipped, he gave the model a bash tool, mostly because it was the example in the documentation. To test what the model could do, he asked it: what music am I listening to? Claude wrote AppleScript to query his music player. This was Claude 3.5 Sonnet. He had what he describes as his first "feel the AGI moment."

"At Anthropic, the way that we thought about it is we don't build for the model of today. We build for the model six months from now. That's actually still my advice to founders that are building on LLMs — just try to think about what is that frontier where the model is not very good at today, because it's going to get good at it." — Boris Cherny, creator of Claude Code (Y Combinator, February 2026)

What followed was three months of not sleeping, working through weekends, shipping internally, iterating. Cherny gave the terminal app to colleagues for dogfooding within two days of the first prototype. The fact that it was a terminal was an accident — he didn't want to build a UI. That accident turned out to be a design feature: terminals impose constraints that force focus, feel productive without ceremony, and don't require context-switching between environments.

The key strategic insight — build for the model six months out — is worth sitting with. At the time Cherny was building the first version, Claude could barely write code. It was handling maybe 10% of his code, and he still wrote the majority by hand. The bet was that the model would improve into the product, not that the product matched the model's current capability. This is a different design philosophy than most developers apply when building on LLMs: optimize for current behavior, guard against current limitations. Cherny optimized for a model that didn't exist yet.

The same principle extends to the decisions being made now. The teams building agentic infrastructure — agent frameworks, evaluation systems, memory architectures — are mostly building for a model that is stronger than the one they're testing against today. Whether they're right about the trajectory will determine which tools persist.

CUDA in Rust: Nvidia Opens the GPU Compiler

Nvidia's NV Labs published cuda-oxide, an experimental Rust-to-CUDA compiler that compiles standard Rust code directly to PTX — the GPU assembly format CUDA uses. No DSLs, no foreign language bindings, no unsafe C interop. You write idiomatic Rust, annotate a module with #[cuda_module], mark kernels with #[kernel], and cargo builds the whole thing.

This matters for two reasons that go beyond Rust enthusiasm. First, safety. GPU kernel code is notoriously difficult to write correctly — memory aliasing bugs and race conditions in SIMT (single instruction, multiple threads) execution are subtle and hard to reproduce. Rust's ownership system catches a category of these at compile time. The cuda-oxide documentation is honest that it's "safe(ish)" — the borrow checker can't reason about GPU execution semantics the way it does about CPU ownership — but "safer than raw CUDA C" is a real improvement for a space where correctness bugs are expensive.

Second, this is Nvidia publishing this. The company with the most to lose from a competing GPU programming ecosystem is now providing official tooling for an alternative to CUDA C. The context is that ROCm (AMD's CUDA competitor) has been gaining ground, and the CUDA ecosystem's moat has historically been as much about the C toolchain's maturity as about hardware lock-in. Making it easier to write GPU kernels in Rust, without sacrificing access to CUDA's ecosystem, is a defensive play — keep the GPU programmers in NVIDIA's orbit even if they prefer Rust to C. The competitive pressure on CUDA from AMD's ROCm was covered in a previous digest; cuda-oxide can be read as Nvidia's answer to the portability argument.

The Career That Might Have an Expiration Date

Sean Godecke published a piece with a deliberately unsettling title: Software engineering may no longer be a lifetime career. It landed on Hacker News with 389 points and generated 637 comments, which means it touched a nerve.

His argument isn't that AI makes engineers obsolete immediately — it's that the structure of the career may be changing in a way that makes the "professional athlete" analogy apt. Pro athletes have a maximum productive career of roughly fifteen years, after which their body can't keep pace with younger competitors. The tragedy is the athlete who doesn't plan for the transition. Godecke suggests software engineers may be entering a similar dynamic: a window of high-value productivity, increasingly compressed, with diminishing returns as the leverage advantage of AI-augmented younger developers compounds over time.

The crux is a premise he grants but doesn't fully accept: if using AI makes you less skilled over time by atrophying the practice of manual reasoning about code, then you're trading long-term cognitive development for short-term productivity. His comparison to construction workers — who lift heavy objects even knowing it wears down their joints, because that's the job — is deliberately uncomfortable. The market may not care about preserving your skill development.

"If the models are good enough, you will simply get outcompeted by engineers willing to trade their long-term cognitive ability for a short-term lucrative career. I hope that this isn't true. It would be really unfortunate for software engineers. But it would be even more unfortunate if it were true and we refused to acknowledge it." — Sean Godecke

The HN comments split roughly into three camps: those who think the analogy is overblown and that senior engineering judgment becomes more valuable as AI handles implementation; those who agree and are actively planning career transitions; and those who think the real change is that the career becomes more like architecture or medicine — fewer practitioners needed, but those who remain command premium value. All three camps are probably partially right, and it likely varies significantly by domain and company size.

The adjacent question — why use Python if AI writes the code? — follows naturally. If the choice of programming language has historically been about what skilled humans can maintain, reason about, and debug effectively, and those constraints are being relaxed by AI assistants that fluently handle multiple languages, then the utility of Python's readability advantage shrinks. What doesn't shrink is the ecosystem: library breadth, deployment tooling, hiring pools. Language choice becomes an ecosystem question more than a cognitive ergonomics question.

What This All Means

  1. The build pipeline is the production surface. The TanStack attack used no zero-days — just three documented, well-understood GitHub Actions weaknesses chained together. The supply chain is not an edge case threat; it is the primary threat vector for projects with wide downstream usage. Every pull_request_target workflow deserves the same scrutiny as a database migration.
  2. AI security is bidirectional and accelerating. Mythos finding one vulnerability in deeply-scanned curl is impressive. Criminals using similar tools offensively is the inevitable complement. The window in which defenders have an AI advantage over attackers is finite, and it may already be closing. Continuous AI-powered scanning is the new baseline, not a premium feature.
  3. AI-era org restructuring has a recognizable shape. GitLab's changes — fewer management layers, more autonomous teams, AI agents handling coordination overhead — will be replicated broadly. The org structures built for human coordination bottlenecks are not the org structures suited for AI-mediated coordination. Companies that redesign proactively will move faster than those restructuring reactively.
  4. Build for the model six months out, not the one you're testing with today. Boris Cherny's principle has aged well: Claude Code was built when Claude could barely write code, premised on the belief the model would improve into the product. Teams building agentic infrastructure now are making the same bet — the frameworks they're building assume models with stronger reasoning, longer context, and more reliable tool use than currently exist. They're probably right.
  5. The software engineering career inflection is real but not uniform. The question isn't whether AI changes the job — it clearly does. The question is what the second-order effects are on skill development, career longevity, and the distribution of value across experience levels. The honest answer is that we don't have enough data yet, which is exactly why thinking about it now matters.
